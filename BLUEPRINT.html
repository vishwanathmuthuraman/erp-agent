ERP Agent Testbench

Status: documentation blueprint only — application, runner, simulator, tests and measured results are not implemented. The supplied JSON files are original synthetic design examples with expected outcomes, not execution results. All implementation tasks are not_started.

Planned outcome: a local testbench that connects an agent to a simulated purchase-order workflow, introduces controlled failures, and produces a reviewable acceptance/regression report. Its four fault classes are duplicate execution, policy/approval violations, schema mismatches and partial execution.

Start here

  1. Read requirements and architecture.
  2. Open the build plan and task tracker. Begin T01; dependencies determine the next task.
  3. Inspect the clean example, faulty example and their guide.
  4. Implement the local vertical slice before generating a full benchmark or adding a model provider.
  5. Use evaluation and definition of done to decide what can be claimed.

There is no installation or launch command today. Commands in the build plan describe a future CLI contract and will fail until its prerequisites are implemented. No API key is needed for the planned deterministic reference agent.

This project must work independently: a separate reference agent is included in the planned implementation; no sibling project, live ERP or hosted service is required.

Reports will describe synthetic benchmark performance under specified controls. They will not certify an agent, establish production safety, or imply affiliation with a named ERP vendor. The simulator is a deliberately limited contract implementation.

01 — Product requirements

Status: proposed requirements; none is marked implemented. Start here.

Problem and end goal

An automation owner sees an agent complete one purchase-order demo. After a lost response the agent repeats the amendment, or it declares success although the order and commitment records disagree. A happy-path demonstration does not establish behavior under those conditions.

Version 1 provides a bounded way to inspect these failures before handover or after a change. A reviewer must be able to connect every reported failure to an observable record, rule and event. Expected demand from implementation firms is a hypothesis; existing simulation and evaluation products overlap with this idea.

Users and stories

User Story Successful interaction
Implementation engineer Connect an existing agent without changing its planning logic. Adapter conformance passes; the agent uses only simulator tools.
Automation owner Establish the rules a deployment must meet. A versioned rule manifest identifies each control and its scope.
Reviewer Understand a failed handover test. Report shows an assertion, expected/observed values and evidence IDs.
Maintainer Detect regressions after a change. Paired report identifies newly failing rules and improvements separately.
Independent reproducer Re-run a published experiment. Pinned environment and artifacts reproduce deterministic verdicts.

Bounded workflow

Use one synthetic supplier, one currency per case, one order line and integer quantity changes. An agent reads an order and policy, locates a pre-existing approval, submits an amendment, checks completion and returns a status. The simulated ERP records the updated order and a commitment entry. A controlled interruption can occur between those two writes.

Approval refers to the business operation and approved payload; it is not inferred from natural-language enthusiasm. Business operation ID, idempotency key, request hash and transport attempt ID have separate meanings. Reusing an idempotency key returns the prior result; changing it may perform the operation twice. This deliberately models a provider that deduplicates request keys rather than business intent.

In scope: local deterministic simulator, JSON contracts, external-agent adapter, independent reference agent, seeded faults, three check suites, CLI, static report and CI example. Optional after core completion: localhost FastAPI viewer and an explicitly enabled model-backed agent.

Out of scope: real purchasing, payments, ERP certification, production access controls, general ERP emulation, arbitrary user-code sandboxing, unbounded multi-agent workflows and automatic repair of real transactions.

Functional requirements

ID Requirement Observable acceptance
FR-01 Validate cases before execution. Unknown fields, wrong types and invalid cross-record references fail before any write.
FR-02 Create isolated state per execution. Two concurrent cases cannot read or change each other's database or artifacts.
FR-03 Support the documented purchase-order state machine. Clean execution creates one amendment and one matching commitment.
FR-04 Provide an independent adapter contract. A second stub agent works through the same interface as the reference agent.
FR-05 Supply a deterministic reference agent. Clean retry reuses its key, checks operation status and completes correctly.
FR-06 Separate disturbances from defective behavior. A timeout recovered correctly is a clean case; a changed retry key can expose a duplicate.
FR-07 Represent four fault classes. Each class has a reviewed behavior-changing mutant and a clean counterpart.
FR-08 Produce bounded, ordered observable evidence. Tool request/response, logical time, state transition and terminal status have stable references.
FR-09 Keep ground truth outside agent and suite inputs. Fixture label, mutation configuration and expected verdicts are absent from observation bundles.
FR-10 Evaluate smoke, state and hybrid suites. All receive the same immutable bundle and declared budget; skipped checks remain visible.
FR-11 Distinguish failure, error and incomplete evidence. Invalid input or runner crashes cannot masquerade as a detected agent defect or pass.
FR-12 Generate JSON and readable reports. Each finding links rule, evidence, expected value, observed value and severity.
FR-13 Compare candidate and baseline releases. Only matching case/protocol manifests are paired; new failures appear individually.
FR-14 Enforce execution and checking budgets. Exceeding wall time/tool calls stops work and returns an explicit incomplete/error record.
FR-15 Run offline by default and reproduce runs. Reference demo needs no secrets/network; replay preserves substantive verdicts.
FR-16 Support CI and public handoff. Expected demo failures, unexpected regressions and infrastructure errors have distinct exits.

Nonfunctional requirements

Money is signed integer minor units with an explicit currency; no binary floating-point business arithmetic. Case ticks are integers, separate from measured wall time. Validate all JSON at boundaries; reject unrecognized schema versions. Use explicit SQLite transactions and foreign-key enforcement on every connection. Logs contain synthetic tool evidence, not model secrets or hidden reasoning.

Proposed limits: 20 agent tool calls, 100 logical ticks and 30 seconds wall time per execution; 100 evidence reads and five seconds per suite evaluation. These are initial development budgets, not performance measurements. Freeze revisions before held-out evaluation. The model path is disabled by default and requires an explicit provider, model, spend cap and authorization.

Discovery before commercial extension

Ask implementation engineers for the last escaped retry, approval, schema or partial-write problem; the artifacts they used; time to diagnose; current tools; and who accepts deployment risk. Record negative findings. Access to real data, integrations and paid work is not assumed. Public examples stay synthetic even if discovery informs scenario design.

02 — Proposed architecture and layout

Status: design contracts, not implemented APIs. Requirements.

Boundaries

flowchart LR
    Case[Case and hidden mutation spec] --> Runner[Isolated execution runner]
    Runner --> Agent[Reference or external agent adapter]
    Agent --> Tools[Restricted tool client]
    Tools --> Sim[Local ERP simulator]
    Sim --> DB[Per-run SQLite state]
    Runner --> Bundle[Sanitized immutable observation bundle]
    Bundle --> Suites[Smoke / state / hybrid suites]
    Suites --> Report[Findings and report]
    Oracle[Hidden expected outcomes] --> Scorer[Offline benchmark scorer]
    Report --> Scorer

The agent sees task, tool schemas and tool results. It cannot read fixture files, databases, expected results or mutation controls. Suites see the same sanitized observation bundle; only the scorer receives ground truth. Reference-agent behavior and the checking code live in separate modules. Checker code must not import mutation or expected-result modules.

An external adapter is a trusted integration supplied by the operator. Version 1 does not promise to contain malicious Python code. Running arbitrary agent code in the runner process would defeat isolation. For supported external adapters, use a separate process with a minimal environment and a restricted RPC/tool channel; no direct database mounts. Network isolation must be verified for the chosen execution environment, not inferred from localhost URLs. Untrusted adapters require a later, independently reviewed sandbox.

Reference-agent mutants are controller-selected specimen variants, not options exposed to the agent. External agents receive disturbances through the tool boundary; do not pretend to mutate their internals unless a separately documented test wrapper supports that operation.

Interfaces

All interfaces below are proposed version 0.1. Choose one JSON serializer and canonical request-hash definition before implementing hashes.

Boundary Input Output / rule
AgentAdapter.run public task, restricted tool client, limits terminal completed, review_required, failed or incomplete; summary and operation IDs
read_order order ID quantity, integer unit price, currency, supplier, version
read_policy supplier ID active status, policy version, amount threshold
read_approval operation ID approved quantity delta/price, authority limit, expiry tick, policy version
apply_amendment operation/order IDs, quantity delta, unit price, approval ID, idempotency key operation ID, status, updated order version; validates schema before side effects
get_operation operation ID all matching attempt records and statuses; exposes ambiguity rather than selecting one silently
resume_operation server operation-record ID, original idempotency key finish missing commitment for that record without reapplying the order delta
CheckSuite.evaluate immutable observation, rule manifest, checking budget structured findings, checked/skipped rule IDs, elapsed work, verdict

RPC requests carry protocol_version, request_id, method, params; responses carry the same ID and either result or a typed error. Errors distinguish invalid arguments, policy denial, timeout/unknown commit state, unsupported operation and infrastructure failure. Timeouts never imply that the server rolled back.

Local execution does not require an HTTP service. The planned subprocess adapter communicates JSON Lines through pipes; the parent controls simulator access. An optional FastAPI layer exposes read-only report routes (GET /runs, /runs/{id}, /runs/{id}/findings) on 127.0.0.1. No write route, authentication claim or Internet deployment is included.

Data and state

Proposed SQLite tables: orders, approvals, policies, operation_attempts, commitments, events. Each database belongs to one run. operation_attempts has a unique idempotency key; business operation IDs are indexed but deliberately not unique, so the checker can detect repeated intent submitted under new keys. This provider-like contract must be explicit in every report.

An operation moves requested → validated → order_applied → committed. Denial occurs before order_applied. For partial-execution tests, an injected interruption may leave order_applied without a commitment. Recovery uses the recorded intermediate state. completed is legitimate only once the matching commitment exists. Do not claim atomicity across these modeled steps.

Initialize each connection with sqlite3.connect(..., autocommit=True), enable PRAGMA foreign_keys=ON, and verify the pragma returns 1 before setting connection.autocommit = False for explicit commit/rollback work. SQLite cannot change foreign-key enforcement inside an active transaction; setting the pragma after starting that transaction would silently leave the intended control disabled. Limit version 1 to one writer per database. Concurrent scenarios get separate files; parallel clients within a scenario use a deterministic serialized scheduler. This makes race coverage limited and disclosed.

Request hash covers operation ID, order ID, quantity delta, unit price, currency and approval ID. It excludes transport attempt ID and idempotency key. A changed request with the same key returns a conflict. A matching key returns the original recorded operation/result even after response loss. Approval binding checks the approved business fields and current policy, not just possession of an approval ID.

Observation and report contracts

An observation contains schema_version, opaque case_token, execution_id, task, initial/final business snapshots, public policy/approval records, ordered events, terminal agent result, execution budget usage and artifact hashes. Export no fault label, mutation name, expected rule list, split label or template group. It may include facts from which a defect can be inferred; hiding valid evidence would make evaluation artificial.

Apply the allowlist recursively to both agent inputs and suite observations. Replace descriptive scenario/run IDs and filenames with opaque tokens; omit controller paths and mutation annotations embedded in auxiliary metadata. Hash only the sanitized artifact in the runtime view. Keep the reversible provenance map in the controller and join it after scoring for the human report. Preserve genuine business fields and observed tool errors. Planned leakage tests plant sentinel labels in nested metadata, filenames and IDs and assert that neither evaluated interface receives them.

Events have event_id, sequence, logical tick, actor, tool, request ID, business operation ID, request hash, public arguments/result or typed error, and affected record IDs. Full model reasoning is neither requested nor stored. Preserve external content as data; HTML-escape it in reports.

Findings contain rule ID, severity, evidence IDs, expected condition, observed value, and explanation. Suite verdicts are pass, fail, inconclusive, error. Benchmark classification is computed later. A report also records case/protocol/code/adapter versions, limits, measured runtime, optional token/cost usage and unsupported behaviors.

Viewer layout

Static report first: a header with run identity and synthetic evaluation label; status cards for evaluated/failed/inconclusive/error counts; a sortable case table; and a detail panel showing expected condition, observed state, ordered tool evidence and state diff. Regression view has separate “new failures”, “fixed failures” and “unpaired cases” tables. Keyboard navigation, text labels and readable contrast are required; color alone never communicates status. The report remains readable without JavaScript.

03 — Sequenced build plan

Every command in this document is FUTURE and unimplemented unless it is a standard dependency-tool command. Do not run this as an existing application. All paths below are relative to the project root. Tracker provides task-level dependencies and estimates.

Prerequisites: a terminal, an editor, Python 3.12 and uv. Their presence is not assumed. Install uv using its official installation instructions and verify uv --version; record the version used. uv can provision Python 3.12 during the future setup. No dependencies were installed as part of this blueprint.

A. Establish the contract — T01–T05

Inputs: requirements, supplied schemas, clean/fault design examples. Review the operation/approval semantics and decide licenses. Create pyproject.toml, a source package, .python-version and the erp-bench entry point. Preserve existing documentation; do not overwrite it with a project-generator template. Select a small dependency set: JSON Schema validation, pytest and a formatter/linter; use standard-library SQLite and argparse initially.

Future setup commands after writing the package manifest:

uv python pin 3.12
uv add jsonschema
uv add --dev pytest ruff
uv lock
uv sync --frozen
uv run erp-bench --help

Expected output: a locked environment and honest CLI help, with unfinished commands explicitly unavailable. Implement schema validation plus cross-record validation; never accept a schema-valid dangling approval reference. Checkpoint A: malformed inputs fail before state creation, and every supplied example validates.

B. Build one clean execution — T06–T12

Create storage.py, simulator.py, observation.py, adapter contracts and deterministic reference agent. Implement order read, policy/approval read, amendment, operation lookup and resume. Keep source writes transactional within each modeled step. Implement a fresh run directory and database per execution. Add test coverage for normal state transitions, approval expiry, same-key/different-payload conflict and idempotency.

Future commands after T12:

uv run pytest tests/unit tests/integration
uv run erp-bench validate examples/clean-retry.case.json
uv run erp-bench execute --case examples/clean-retry.case.json --agent reference --out artifacts/clean-demo

Expected output eventually: manifest.json, observation.json, events.jsonl and a local database under the new output directory. Refuse an existing output directory unless a distinct run ID is provided; never overwrite a prior run silently. The cleaned observation is the only input to suites.

Checkpoint B: one timeout-after-commit followed by a same-key retry yields quantity 13, one committed operation and one commitment. This is a target, not a recorded result.

C. Expose four defect classes — T13–T18

Create controller-only mutation hooks and disturbance scheduling. First implement response loss independently of retry-key mutation. Then implement approval bypass, schema-coercion/error handling and incomplete-operation success mutants. Give each mutation an explicit activation condition and traceable evidence. Add clean variants where the disturbance occurs but the reference system behaves correctly.

Create the independent subprocess adapter with a benign stub agent. Test protocol-version rejection, tool allowlisting and budgets. A process crash or invalid protocol is an adapter/runner error, not a detection success. Checkpoint C: all four mutants change behavior under at least one reviewed case; clean counterparts satisfy their intended rules. Quarantine equivalent, unreachable and ambiguous mutants.

D. Implement checking and reports — T19–T26

Build smoke, state and hybrid suites as pure readers of one observation. Define the rule catalog before implementations. Build JSON findings, static HTML and CLI return codes; then add version comparison. Validate render escaping with a synthetic string containing HTML markup.

Future commands after T26:

uv run erp-bench execute --case examples/duplicate-retry.case.json --agent reference --out artifacts/fault-demo
uv run erp-bench check --observation artifacts/fault-demo/observation.json --suite all --out artifacts/fault-checks
uv run erp-bench report --checks artifacts/fault-checks --out artifacts/fault-report.html
uv run erp-bench compare --baseline artifacts/baseline --candidate artifacts/candidate --out artifacts/comparison

The case controller applies the specified specimen mutation during execution; suites do not receive it. Expected example: smoke passes, state/hybrid identify duplicate application. check returns exit 1 for detected failure; that is an intentional demonstration outcome. compare rejects missing or incompatible baseline/candidate manifests with exit 2. The example directories for comparison do not exist today.

Checkpoint D: every finding links to real observation evidence; incomplete observations never become clean passes; compare reports a seeded new failure rather than hiding it in an average.

E. Freeze and evaluate — T27–T33

Construct 40 development cases; use them to tune rules and limits. A separate reviewer authors or withholds the 120 test executions and oracle files. Freeze code, protocol, group split and budgets first. Run mutant validity checks outside the suites, then capture observations once and evaluate every suite on those identical artifacts.

Future benchmark commands after T31 and reviewer handoff:

uv run erp-bench benchmark --manifest private/heldout/manifest.json --suites smoke,state,hybrid --out artifacts/heldout-run
uv run erp-bench score --run artifacts/heldout-run --oracle private/heldout/oracle.json --out artifacts/heldout-score
uv run erp-bench report --checks artifacts/heldout-run --scores artifacts/heldout-score --out artifacts/heldout-report.html

private/heldout is a proposed ignored directory, not a supplied dataset. Labels must be inaccessible to agent/suite processes. Benchmark exit 0 means the evaluation pipeline completed, not every specimen was safe; expected faulty specimens are part of its dataset. Pipeline errors return 2. Scoring must retain every assigned case, with invalid/error counts and exclusions explained.

Checkpoint E: exactly 120 eligible executions × three suites = 360 suite evaluations. Do not silently reduce the denominator, rerun a failing case until it passes, or adjust thresholds after seeing test outcomes.

F. Independent reproduction and release — T34–T38

Generate a reusable CI workflow only after local commands are stable. The CI job installs Python 3.12, synchronizes the lockfile, validates examples, runs meaningful tests and publishes bounded synthetic report artifacts. An acceptance wrapper distinguishes an expected fault fixture from an unexpected regression.

Ask a second person or use a separate clean environment to repeat the deterministic release. Resolve findings, record limitations and choose a release gate outcome. Publish only after the handoff checklist, license gate and claim review pass.

Future release verification:

uv sync --frozen
uv run ruff check .
uv run pytest
uv run erp-bench demo --out artifacts/release-demo

demo must verify the known clean/fault expectations and return 0 only when both match, with a report still showing the fault. It does not treat all agent runs as passing.

Optional T39 adds the local report viewer only after the core release. Its future command is uv run uvicorn erp_agent_testbench.web:app --host 127.0.0.1 --port 8000, after adding the dependencies and implementing web.py. UI work must not delay an inspectable CLI/static report.

Resume rules

Select the lowest task whose dependencies are done. Record exact outputs and evidence before changing status. If a requirement changes, update the FR, affected tests, protocol version and task acceptance together. Keep unfinished commands labeled future; do not create placeholder passing tests or fabricated result files to make a milestone appear complete.

04 — Evaluation protocol

Status: proposed protocol 0.1; no executions, scores or accepted benchmark cases exist yet. The two supplied examples demonstrate contracts and are not a completed dataset.

Question and comparison unit

Which checking approach detects seeded workflow failures while limiting false alarms and checking work? The study evaluates check suites applied to observed executions, not three different agents. Capture each execution once, then give the identical sanitized artifact to all three suites. This removes agent randomness from the primary comparison.

Suite Planned checks Deliberate limitation
Smoke Terminal completion, parseable output, expected operation reference and presence of an updated order Does not establish uniqueness, correct final state or approval ordering.
State Smoke plus record/schema, final quantity, unique intent, commitment consistency and approval binding invariants May miss a transient violation later hidden by repair.
Hybrid State checks plus ordered tool/approval/retry/partial-completion rules More checks can increase false positives and work.

All suites receive the same records, event history and public policy. They choose what to inspect; stronger suites do not receive additional ground truth. All are deterministic in the primary study. Adding an LLM judge would be a separate experiment requiring its own frozen protocol and budget.

Dataset allocation

Partition Duplicate Approval/policy Schema Partial execution Total
Development faulty 5 5 5 5 20
Development clean 5 5 5 5 20
Held-out faulty 15 15 15 15 60
Held-out clean 15 15 15 15 60

There are 40 development cases and 120 held-out executions. Evaluate each held-out execution with three suites: 360 suite evaluations, each potentially containing multiple assertions. Do not describe this as 360 independent incidents or 360 individual assertions.

Keep related workflow templates, parameter variants, clean/fault pairs and mutation-family variants in the same partition. Categories may recur across partitions; an instantiated template must not. Save template-group IDs in a controller-only split manifest, check overlaps automatically, and manually inspect structural similarity. Different names or random seeds do not make a reused template independent.

A reviewer holds test fixtures and oracle files outside the agent/suite environment until code and protocol hashes are frozen. Authoring all test labels yourself limits blinding; disclose that if independent review is unavailable. Once held-out cases are published, they become public regression cases; future claims require a new withheld set. Never relabel a publicly seen corpus as unseen.

Disturbances, mutants and ground truth

A disturbance is a response loss, denial, changed interface or interruption. A mutant is a deliberate defect in the specimen agent/connector, or an explicitly stated system component. A disturbance that is handled correctly is a clean case, even if it produces retries.

For each candidate mutant: prove the trigger executes; run the unmutated counterpart under the same schedule; inspect the resulting behavior; identify the violated rule; and have a reviewer confirm it without using suite predictions. Require an observable defect at the supported interface. Non-triggered, equivalent and ambiguous mutants are quarantined before sealing; preserve counts and reasons. No post-result replacement to improve detection scores.

Clean cases must be independently checked for validity, including successful recovery, legitimate denial/review where the task requires it, and benign schema evolution within the declared contract. The suite must know the public task's accepted terminal statuses. Hidden oracle labels cannot supply that business rule.

Budgets and fairness

Primary execution caps: 20 tool calls, 100 ticks and 30 wall seconds per specimen. Each suite gets at most 100 evidence reads and five wall seconds. Define one evidence read as one requested snapshot or event object; file reads alone are not the unit. Record actual reads, assertions and elapsed time. Freeze the machine description, environment, concurrency and adapter versions. Use a warm-up outside scored cases and randomize suite order or rotate it deterministically.

Timeout, missing evidence and runner failure are not passes or detections. Report fault detection on all 60 assigned faulty executions and false alarms on all 60 clean executions, alongside coverage and inconclusive/error rates. If eligibility defects are discovered after sealing, show both original-assignment counts and a transparently corrected analysis; rescore all suites consistently.

Measures

  • Fault detection: faulty executions with at least one valid failure finding / 60. Also report each class / 15.
  • Clean false-alarm rate: clean executions with a failure finding / 60. Unsupported findings are not discarded silently.
  • Complete coverage: evaluations yielding pass/fail with all intended checks complete / 120, per suite. Report incomplete/error cases separately.
  • Localization: detected faulty executions identifying an oracle-accepted rule and causal evidence / detected faulty executions. Publish the rule-mapping policy before scoring.
  • Checking work: median/p95 reads, assertions and runtime; execution work is reported separately and identical across suites.
  • Regression rate: cases that pass in the baseline release and fail in the candidate / cases that passed in baseline with comparable observations. If none pass, rate is undefined. List new critical failures individually; a fixed old failure cannot cancel a new critical failure.

For release comparison, rerun the same frozen scenario set with candidate and baseline agent versions, then apply one frozen suite version. Separate a checker change from an agent change; do not compare unlike protocols. Report lost coverage and newly errored cases as regressions in evidence quality, not successful tests.

Use paired differences between suites and uncertainty clustered by shared template group. Synthetic family balance is a design choice, not an estimate of real defect prevalence. Do not claim precision on live workloads from a 50/50 constructed corpus. Three suites on the same execution are correlated observations.

Replay, artifacts and optional model runs

Manifests record case hashes, split/group manifest hash, schema/protocol versions, code commit when available, lock hash, adapter and rule versions, seed, schedule, budgets, machine/runtime and artifact hashes. Stable normalized state and verdicts should reproduce; volatile timestamps/run IDs are compared separately.

Store raw observations, predictions and ground truth separately. Scoring joins opaque IDs only after evaluation. An optional model experiment needs a fixed subset, repetitions, model/provider version, prompt hash, token limits and a separate spending cap. It cannot be silently folded into the 360 deterministic suite evaluations.

Negative results are valid outputs. If hybrid checking adds no useful detection or too many alarms, report that finding and preserve the original protocol.

05 — Definition of done

All targets below are pending. No test has been implemented or passed, and no performance target is achieved. Evaluation protocol.

Completion gates

Gate Required evidence
Contract complete Every example validates; invalid references/types/versions fail before writes; adapter and rule versions documented.
Functional slice Independent reference and stub adapters complete the clean task; clean timeout recovery produces exactly one effect.
Fault coverage Four reviewed development defects yield correct hybrid findings; clean counterparts do not fail; missing evidence cannot pass.
Isolation Fresh state per run; no cross-case reads/writes; oracle/mutation fields absent from adapter/suite inputs; default run makes no external calls.
Reproducibility Separate clean installation repeats normalized deterministic state and suite verdicts for all released examples.
Evaluation integrity 40 development and 120 held-out cases documented; no split-group overlap; 360 suite evaluations with complete denominators and errors.
Operational report Every finding has rule/evidence/value links; report opens locally; injected HTML renders as text; regression view exposes new failures.
Public release Ownership/license decisions resolved; claims match evidence; protocol, reproducible artifacts and limitations available.

Initial performance hypotheses for an acceptance-focused v1: hybrid detects at least 54/60 held-out faulty cases, at least 12/15 per class, with at most 3/60 clean false alarms and zero missing records in the evaluation inventory. A new critical regression blocks release of the affected reference-agent version. Freeze these targets before the test set is opened; they are proposed engineering acceptance thresholds, not validated industry standards.

Missing a performance target does not justify changing labels, removing hard cases or hiding results. Publish a clearly labeled experimental report with unmet targets; keep the acceptance-focused release gate open. A complete honest study and an accepted product release are different states.

06 — Sources and design rationale

Research checked 11 October 2026. Short paraphrases below preserve the distinction between reported findings and this project's choices. No firm endorses this project.

Problem evidence

PwC, 2025 Responsible AI survey. Half of surveyed leaders identified translating principles into scalable operational processes as their largest hurdle. The survey covered 310 US business leaders at director level or above, fielded September 26–October 2, 2025. PwC also discusses testing, monitoring and feedback as operational capabilities. Official report.

Project inference: repeatable workflow tests may help an automation owner turn stated controls into inspectable evidence. The survey does not measure demand for this testbench, willingness to pay, or the frequency of these four defects. Its self-reported US sample is not a universal enterprise failure rate.

Deloitte, State of AI in the Enterprise, January 2026. Page 20 reports that 21% of companies surveyed had a mature governance model for autonomous agents. The report describes 3,235 senior respondents across 24 countries, fielded August–September 2025, supplemented by 15 interviews. The sample targets organizations and leaders involved in AI. Official PDF, governance page 20 and methodology page 40.

Project inference: a concrete acceptance process is worth testing with implementers. The statistic does not establish that testing alone closes the governance gap, nor that this simulator predicts production reliability.

Existing approaches and limits of novelty

Veris markets policy/workflow benchmarks in simulated systems. Fabrik describes stateful workflow tests, reviewed business rules and release comparisons. These are vendor descriptions, not independently verified performance. The proposed contribution is a small inspectable workflow contract, an explicit fault protocol and reproducible comparison. Generic simulation, regression testing and agent tracing are established approaches.

Cost model

The deterministic reference path is designed for local execution with zero external model calls. That does not make labor or computing free. Record engineering hours, reviewer hours, machine runtime, storage and any CI charges separately.

Planned primary workload: 120 captured executions plus 360 checking passes. At the caps, capture wall time is 3,600 seconds and checking wall time 1,800 seconds, excluding setup, validation, artifact generation and development work. These are arithmetic upper bounds for serial capped steps, not measured runtimes or a throughput claim.

For optional models: estimated cost equals input tokens × quoted input price plus output tokens × quoted output price, divided by the price unit, plus any tool charges. Record provider/model, price date, currency, retries and an explicit hard spend cap. No provider, subscription, deployment or spending is authorized by this document.

Commercial discovery should measure time to prepare cases, investigate a failure and repeat a release test. Proposed value remains unproven until observed with the intended users. Treat a useful open demonstration, a successful handover and a paying deployment as separate outcomes.

08 — Public release and handoff

The current deliverable is prepared for authorized public GitHub sharing as a documentation blueprint, not an application release. License selection is pending; no code, documentation or synthetic-data license grant is supplied. Do not publish screenshots, badges, pass rates or a working-demo claim until those artifacts actually exist. Completion gates.

Release checklist

  • [ ] Decide code, documentation and synthetic-data licenses; confirm ownership and third-party terms. Do not infer permission from public availability.
  • [ ] Verify every public fixture is synthetic; review logs, screenshots, configuration, filenames and version-control history for private material.
  • [ ] Confirm .env, private/raw datasets, runtime databases and generated working output remain excluded. A .gitignore does not remove already tracked content or rotate credentials.
  • [ ] Replace future commands with verified commands only after implementation. Preserve the blueprint status on incomplete components.
  • [ ] Reproduce from a clean installation with the lockfile and record the environment, hardware, code and artifact hashes.
  • [ ] Validate the full case inventory, split groups, mutant audit and evaluator/agent separation.
  • [ ] Publish protocol, rule definitions, denominators, false alarms, errors, exclusions and limitations alongside result tables.
  • [ ] Separate expected fixture output from measured results; mark every report with its actual execution status.
  • [ ] Explain that published held-out cases are thereafter public regression data.
  • [ ] Render-check static reports at desktop and narrow widths; inspect escaping, evidence links, keyboard navigation and readable status labels.
  • [ ] Include one reference-agent example and one independent adapter demonstration; neither may depend on another repository checkout.
  • [ ] Record remaining unsupported ERP operations, concurrency limits and the trusted-adapter boundary.
  • [ ] Review claims: no certification, guaranteed production safety, unsupported novelty or unmeasured customer impact.
  • [ ] Obtain independent review and record substantive feedback and fixes accurately.

Proposed release bundle

After implementation, hand off a source archive, resolved license files, lockfile, protocol/rule manifests, original synthetic examples, clean/fault demo, JSON/HTML report, evaluation tables, reproduction instructions and known-limitations note. Approved small report examples may be copied into a deliberately reviewed release/ directory; routine artifacts/ output remains ignored. Do not publish an empty results folder as evidence.

An operator handoff should explain installation, adapter setup, local isolation, budgets, execution versus suite exit codes, locating evidence, resetting only a named run, and comparing releases. Include a rollback plan for reverting testbench code/configuration; this is not a promise to reverse business transactions.

Suggested factual project description

Until implemented: “A documented blueprint for a local ERP-agent testbench covering retries, approvals, schema errors and partial execution. Includes original synthetic fixtures and a proposed evaluation protocol.”

After verified release, replace that sentence with the actual implemented scope and measured result, explicitly naming synthetic data, dataset size, relevant limits and remaining failures. Link the release and report. Do not insert anticipated results into publication drafts.

Maintenance

Version contracts when fields or semantics change; version the benchmark when cases or labels change. A checker correction requires all affected comparisons to be rerun consistently. Preserve old manifests and explain corrections. Revalidate dependencies and publishing claims on every release. Track issues from actual users without exposing their data.
